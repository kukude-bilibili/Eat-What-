# 校园/校外菜单库：调研与设计（2026-09-26）

> 结论先行：**没有任何外卖平台提供"读取他人商家完整菜单"的合法公开 API**。所有平台 API 都是给"商家管理自己的店"或"服务商"用的。因此数据来源走「地图 POI 店铺骨架 + 用户导入（AI 拍照为主）+ 菜单包众包」的混合方案，平台数据合作列为远期商务选项。

## A. 需求复述与关键假设

**复述**：把现有"自定义菜库"升级为统一的菜单库体系——校园侧按食堂/楼层/窗口组织（弱化店铺），校外侧按店铺组织（店名/品类/位置/营业时间/菜单），两类都归入 Menu 体系但保留结构差异。导入要"低负担"（靠流程设计而非文案）。先调研平台数据可行性，不可行则用户导入/众包。

**关键假设**：
1. 用户主体是同一校园的学生，菜单库的冷启动由少数"热心录入者"（AI 拍菜）完成，多数人只导入菜单包
2. 校外场景是"学校周边 1-3km"的高频商家（奶茶/快餐/烧烤/面馆），不是全城外卖
3. 暂无后端账号体系，数据在本机 + 菜单包文本传播
4. 平台数据不作为 MVP 依赖（调研结论见 D）

## B. 对象模型/数据结构

```
MenuLibrary（库：一个"吃饭的世界"）
  ├─ kind: 'campus' | 'offcampus' | 'personal'
  └─ Menu[]（菜单）
       ├─ 校园 Menu：title="二食堂 3F 麻辣香锅窗口"，shopId = 空（弱化）
       └─ 校外 Menu：title="华莱士（东门店）"，shopId 必填
       ├─ source: 'manual' | 'ai-scan' | 'pack' | 'poi'
       └─ updatedAt（展示"多久前更新"，数据新鲜度可感知）
  └─ Shop（校外店铺锚点，校园为空）
       ├─ name / category（品类）/ hours（营业时间）
       ├─ location: { lat, lng, address?, distanceM? }（来自高德 POI 或用户手填）
       └─ source: 'poi' | 'user'
```

TypeScript 草案：

```ts
interface MenuLibrary { id: string; name: string; kind: 'campus' | 'offcampus' | 'personal' }

interface Shop {
  id: string
  name: string
  category: string            // 快餐/奶茶/烧烤/川菜…
  location?: { lat: number; lng: number; address?: string; distanceM?: number }
  hours?: string              // 文本，如 "10:00-22:00"
  source: 'poi' | 'user'
  updatedAt: number
}

interface Menu {
  id: string
  libraryId: string
  title: string               // 校园="窗口名"，校外=店铺名（冗余一份便于展示）
  shopId?: string | null      // 校园 = null；校外 = Shop.id（必填）
  kind: 'campus' | 'shop'
  source: 'manual' | 'ai-scan' | 'pack' | 'poi'
  updatedAt: number
}

interface Dish {
  id: string
  menuId: string              // 菜属于哪份菜单（校园=窗口，校外=店铺）
  // …其余字段与现有 Dish 一致：name/price/spicy/type/tags/meals/scenes/blurb
}
```

要点：
- **统一性**：转盘匹配只看 Dish 的字段（时段/辣度/预算/忌口），不关心 Menu 类型——现有匹配器零改动
- **差异性**：展示层用 `Menu.shopId` 区分——校园显示"窗口路径"，校外显示"店铺卡片（品类/距离/营业时间）"
- **迁移**：现有 `customDishes` 每条生成 `menuId`，归入一个 personal Menu "我的菜库"，数据无损

## C. 导入体验方案（流程设计，不写 UI 文案）

原则：**按"用户手里有什么"分流，而不是按技术分流**；AI 做打标，用户只做"确认与纠错"。

| 用户手里有 | 流程 | 步骤数 |
| --- | --- | --- |
| 食堂/店铺的价目表、灯箱 | 拍照 → AI 识别打标 → 草稿确认（可就地改） → 选归属（哪个窗口/哪家店）→ 入库 | 3 步 |
| 外卖 App 的店铺截图 | 截图 → 同上（AI 识图含价格） | 3 步 |
| 同学发的菜单包 | 粘贴 → 清洗去重 → 入库 | 2 步 |
| 什么都没有，就想加一道 | 表单（现有 DishForm） | 随时 |

减负机制（做在流程里）：
1. **默认归类**：AI 顺手给出类型/辣度/时段/场景猜测，用户只在猜错时改
2. **预览纠错**：草稿卡片就地修正，低置信字段高亮；保存后菜库可继续编辑
3. **增量合并**：同一窗口/店铺再拍一张，按菜名相似度合并，不产生重复
4. **归属先选后识**：进流程先选"校园窗口 or 校外店铺"，识别结果直接挂对位置，避免事后整理
5. **店铺骨架免手填**：校外店铺名/品类/位置来自高德 POI（BYOK），用户只补菜单

## D. 平台数据接入可行性对比

| 平台 | 有无 API | 给谁用 | 能拿到什么 | 拿不到什么 | 合规性 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| 淘宝闪购/饿了么（淘宝开放平台 open.taobao.com / developer.alibaba.com） | 有 | 商家自管理、服务商（聚石塔内调用） | 自己店铺的门店/商品/订单 | **他人商家菜单**；公共数据 API 未开放 | 合规但需商家身份授权 | ❌ 不适用 |
| 美团（developer.waimai.meituan.com 餐饮开放平台） | 有 | 商家/服务商 | 自己店铺的商品/订单管理 | 他人商家菜单 | 合规但需商家/服务商资质 | ❌ 不适用 |
| 美团联盟（CPS） | 有（商品查询/榜单） | 有资质的推广媒体 | 推广元数据：店名/优惠/跳转链接 | 完整菜单、实时价格、库存 | 合规；个人门槛高 | ⚠️ 远期可做"优惠角标" |
| 淘宝联盟（淘宝客，含本地生活物料） | 有（taobao.tbk.* 免费接口，个人认证+媒体备案即可） | 个人可申请 | 推广物料/优惠商品 | 完整菜单 | 合规 | ⚠️ 同上，字段有限 |
| 高德开放平台（Web 服务 POI 搜索） | 有（个人 Key，免费日配额百~千级） | 个人开发者 | **店铺骨架**：店名/品类/坐标/距离/部分营业时间 | 菜单内容 | 合规 | ✅ **校外店铺骨架的最佳来源** |
| 非官方抓取/逆向链接解析 | - | - | - | - | 反不正当竞争风险 + 违反平台协议 | ❌ 不做（不做绕过限制的方案） |

**核心结论**：所有外卖平台把"商品数据"视为商家资产，开放 API 只服务于商家自管理；第三方能合法拿到的只有①地图 POI 店铺骨架②联盟推广元数据。**菜单内容必须由用户/众包产生**——这正好和 AI 拍菜天然契合。

## E. 推荐 MVP 路线

- **M1 模型重构（纯前端，无新依赖）**：引入 MenuLibrary/Menu/Shop，现有 customDishes 迁移（自动归入"我的菜库"personal Menu）；转盘匹配不动
- **M2 校园多菜单**：自建"食堂 → 楼层 → 窗口"两级菜单；菜库页按菜单分组展示；摇中的结果显示"来自哪个窗口"
- **M3 校外店铺骨架**：高德 POI BYOK（定位已在）→ 选坐标周边餐饮 → 勾选要的店 → 生成空店铺菜单 → AI 拍菜往里填；距离显示
- **M4 整库分享**：菜单包从"菜品数组"升级为"带 Menu/Shop 结构的整库包"，导出导入沿用现有剪贴板通道
- **明确不做**：平台菜单 API（无）、链接解析（合规灰）、后端账号（现有剪贴板传播够用）

理由：M1 是地基且零风险；M2/M3 分别补齐两类组织的最小体验；数据来源全链路合法（POI 官方 API + 用户自有数据 + AI 打标）；每一步都可独立发布，中途停下也没烂尾。

## F. 风险、成本、待确认问题

**风险**：
1. 高德免费配额（个人日百~千次）——按需缓存 POI 结果，超配额则降级为手填店铺
2. AI 识别准确率——预览纠错兜底；低置信高亮
3. 众包质量——无账号体系防不了恶意，但菜单包靠熟人传播，信任链天然存在；后续可加"包签名/来源展示"
4. 数据过期——Menu.updatedAt + 展示"3 天前更新"，过期不自动删，靠用户自查

**成本**：M1 约 1 次迭代；M2/M3 各约 1 次；高德 Key 免费；无服务器成本

**待确认**：
1. 校园菜单的层级深度：食堂→楼层→窗口 三级，还是"食堂→窗口"两级？（影响 M2 界面复杂度）
2. 校外店铺要不要"距离排序"进转盘权重？（影响 M3 匹配器）
3. 一个库默认多大：全校 vs 学院/生活区？（影响 M1 的 Library 划分）
4. 高德 Key 走 BYOK（每用户自填）还是你申请一个放配置？（合规上个人 Key 可用，但条款对"分发使用"有限制，BYOK 更稳）
