# 校园/校外菜单库：分支验收标准 与 main 合入流程

## D. 给 research/menu-library-competitor 分支的验收标准

**产出物**：分支上的 `docs/research/competitor-findings.md`（一竞品一节）。

**必须覆盖的竞品范围（≥5 个，两类都占）**：
- 校园场景：任意高校的校园墙/小程序菜单库案例、校园二手/信息墙产品
- 通用/外卖：美团或饿了么用户端的菜单组织方式、下厨房等菜谱类、随机决定类工具（转盘/骰子类）

**每竞品六问（缺一退回）**：
1. 目标场景是什么（谁在用、什么时候用）
2. 内容如何组织（层级？按店铺？按菜？截图为证）
3. 用户如何录入（方式 + 实测步骤数）
4. 数据来源与新鲜度处理（谁维护、多久更新、过期怎么办）
5. 我们可借鉴的 1-2 点（具体到交互或模型字段）
6. 不适用于我们的原因（明确说，防止生搬硬套）

**硬性边界**：
- 不重复平台 API 调研（main 已有 ADR-0002 与 2026-09-26 调研文档，引用即可）
- 不写代码、不给实现建议（那是 feature 分支的事）
- 所有事实性陈述带来源（链接/截图）；猜测标注"推测"

**完成定义（DoD）**：
- [ ] 六问对照表填完（竞品 × 六问矩阵）
- [ ] 结论章：给出"校园库 vs 校外库组织方式"的对照建议 + 推荐采纳点清单
- [ ] 自查通过：无 TBD、无断链、无未标注的推测
- [ ] 分支已推送，commit 信息可读

## E. 分支产出后 main 的合入流程

1. **评审**：main 对照上表逐条检查；不合格按条退回（comment 到对应章节）
2. **蒸馏**：评审通过后，main 把可采纳结论映射进 Schema 草案——确定 SHOP_CATEGORIES 枚举、校园层级深度、菜单包 V2 结构；更新 Schema 文档状态 DRAFT → ACCEPTED；ADR 如需修订在此时修订
3. **实现分支**：从 main 开 `feature/menu-library-model`，实现内容限定为：schema 类型文件 + persist migrate（含备份键）+ 校验函数 + 菜库/结果页 UI 分叉 + 菜单包 V2
4. **验收门**（全过才准合入）：
   - vitest 全过（含新增迁移测试：v1 fixture 无损断言/脏数据不炸/幂等/包 round-trip）
   - tsc 清零、build 通过（H5 与 eat-what-mini 同步评估）
   - 手动回归：旧 localStorage 升级、导出导入 round-trip、转盘全流程
   - H5 部署成功且线上冒烟
5. **合入**：squash 到 main，schemaVersion=2 生效；同步 eat-what-mini 走对应 ISSUE
